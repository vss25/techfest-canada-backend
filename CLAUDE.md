# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start        # production (node server.js)
npm run dev      # development with hot reload (nodemon server.js)
```

`npm test` runs the unit tests in `test/` (node:test, no database or network). No build or lint scripts.

## Architecture

Node.js + Express REST API using **ES modules** (`"type": "module"` in package.json). MongoDB via Mongoose.

**Entry point:** `server.js` — mounts all routes, configures CORS, connects to MongoDB, and handles the Stripe webhook raw body parser (must stay before `express.json()`). It `export default app`; with `TTFC_IMPORT_ONLY=1` (tests only: `test/volunteer-panel-db.test.js` walks every route) it loads no `.env`, doesn't connect, starts no jobs and doesn't listen. Never set it on Render.

## Connect by pass (Oct 24 2026)

The organiser: "one QR for everything", then "for staff it should default to checkin and for other attendees it should be share contact". Scanning someone's ENTRY QR (the door QR, `TECHFEST:<ticketId>`, `services/doorQr.js`) in Network › Scan connects you with the pass holder exactly like their connect QR. Contract C-PASS, shared with the iOS and Android apps and the web app (staff and volunteers get Check in as the default action in the apps; "Share contact instead" calls this).

- **`POST /api/social/connections/by-pass {ticketId, share?}`** (`routes/social.js`, any signed-in app user, the `/api/social` JWT). `ticketId` in any form (`TECHFEST:` or bare, any case, stray spaces). Then as `POST /connections/in-person`: accepted at once, `kind: "inPerson"`, `SocialConnection.via = "pass"` (kept as is when a connect QR scan made the row before), the scanner's `share` applied (a rescan of someone already connected keeps what the scanner picked for them before: the sheet can't know whose pass it is, so it offers the defaults), the person scanned shares what their connect QR sheet says (`contactQrShare`, `applyQrShare`), else their share-by-default items. Unlike a connect QR, the person scanned is told, only when the connection is new (or was a pending request), never from a hidden scanner: a row in their in-app Notifications (`AppNotification` kind `conn`: title "`<scanner>` connected with you", body "Scanned your TTFC pass", `sentBy` / `sentByName` the scanner, `batchId` `conn:<connection id>`, link `ttfc://tab/network`; unread and counted; `GET /notifications` adds `fromUserId`, `avatarUrl`, `connectionId` and leaves it out while the scanner is hidden or blocked either way; deleting the scanner's account removes it) and a push with the same words (kind `conn`, id the connection's, pref `connections`). Removing an accepted connection doesn't exist in the apps, so there's no undo. → 200 connectionDTO + `via: "pass"` + `alreadyConnected` (accepted before this scan). Connection DTOs carry `via` everywhere (`GET /connections` too) when set.
- **Whose pass** (`services/passHolder.js resolvePassHolder`, shared `accountForPass` with the door card in `routes/checkin.js`): the account holding the ticket in `User.tickets` whose name the pass carries (`holderIsAccount`: claimed by them, or the checkout form's name agrees, or the pass names nobody), else the account that claimed the pass record (`claimedBy`), else the account with the pass record's email AND an agreeing name. A ticket a buyer bought for a colleague (another name on it, on the buyer's account or under the buyer's email) is never the buyer: the colleague's own account if they claimed it, else nobody (409).
- **Answers** (`services/passConnect.js`): 403 `{code: "share_off", error: "Contact sharing is off for your pass type."}` without `shareContact` (before any lookup); 404 `{code: "not_found", error: "That isn't a TTFC pass we know."}` for an unknown / malformed code, a pass hidden by staff (ticket or pass record), a Stripe-sync duplicate, a fully refunded pass (from the Stripe sessions this instance already cached, `stripeSales.js cachedStripeSessions`; a scan never calls Stripe), and anyone the scanner can't reach: hidden from the app (their account, their pass, a pass under their email; staff and moderators see them as everywhere), banned, a block either way; 409 `{code: "not_on_app", error: "They haven't joined the TTFC app yet. You can connect once they sign in."}` (no account, or never opened the app and not connected yet); 400 `{code: "self", error: "That's your own pass."}`. Refusals are exactly `{code, error}`: no name, email or ticket of the holder. Not audited, nothing logged.
- **No cap on scans** (the organiser: "Don't keep a cap on scan. but tell people in the app whatever they allow to share, will be shared with the QR code printed on the pass."): no per-person or per-address limit and no 429. The apps say it instead, wherever people pick what they share and under the entry QR on the Pass screen.

Tests: `test/pass-connect.test.js` (QR forms, whose ticket, passes that don't count, the answers and the push), `test/connect-by-pass-db.test.js` (the route against a local mongod: an account's pass with sharing both ways, the push and the Notifications row (nobody else gets one, read is read, a later block hides it), rescans and every QR form, a claimed pass, a pass-only pass with the account's name, a colleague's pass never the buyer, hidden by staff / duplicate / refunded / made up, hidden / banned / blocked like unknown and staff seeing hidden people, not on the app, self, no shareContact, a pending request becoming accepted, a hidden scanner, no cap on scans).
